# inds-benchmark-data

Data sets of the thesis benchmarks as classpath resources (no code), ~1.9 GB. Load them by path with
`org.itmo.inds.testdata.DataSets` (module `inds-testdata`): `DataSets.snapshots(path)`, `DataSets.snapshot(path#id)`,
`DataSets.sequence(path)`; see its Javadoc for an example. Every file is byte-identical to the legacy file it was
copied from; sizes, SHA-256, git blob ids and sources are listed in [MANIFEST.tsv](MANIFEST.tsv). `.gitattributes`
marks the data binary, so git never converts line endings.

All kinds contain a population split into non-domination fronts plus points to insert into it. They differ in the
run that produced them, how many populations and how many points:

| Folder (under `org/itmo/inds/data/`) | Files | Per file | Legacy format / source |
|---|---|---|---|
| `snapshots/generational/{dtlz3d,dtlzNd,zdt}/` | 46 | 10 snapshots of one generational NSGA-II run (population 10 000, at the beginning of generations 0, 10, …, 90), each = 10 000 points in fronts + **one** point generated by NSGA-II's operators to insert. **The data of the thesis Ch. 3 figures** | `FrontStorage` (JSON names: `generations`, `fronts`, `fitnesses`, `nextAddend`); `nds2016/PPSN2016Test`, generator `nds2016/NSGA2Tests` `GetResults` |
| `snapshots/generational/uniform/` | 1 | synthetic set `uniform` (3 objectives): 3 samples of 10 000 points + one point each | same format and source |
| `snapshots/{dtlz3d,dtlzNd,zdt}/` | 46 | 11 snapshots of one steady-state NSGA-II run (population 10 000, after 0, 1 000, …, 10 000 iterations), each = 10 000 points in fronts + the **one** offspring generated next | `FrontStorage`; `nds2018benchmarks` = `nds2016/PPSN2017Test` (2017, the steady-state version of the Ch. 3 data), generator `nds2016/NSGA2Tests` `GetResultsSS` |
| `snapshots/constant/` | 12 | synthetic populations of 10 000 points + one point each: `uniform` (hypercube, 3 samples), `twoLayers` (two parallel hyperplanes, 3 samples), `twoLines` (5 000 fronts of two points, 1 sample); 3, 5, 10, 20 objectives | same format and source as the steady-state snapshots; generator `GetResults` (`generateHypercube`, `generateParallelHyperplanes`, `generateParallelLines`) |
| `sequences/{dtlz3d,dtlznd,zdt}/` | 46 | **one** population (5 000 points in fronts, the initial population of a steady-state NSGA-II run) + the **sequence** of the next 1 001 offspring of that run (the file names say 1000; the generator loops `i <= 1000`) | `DoublesAdditionProblem` (`fronts`, `addends`); `nds2018Cbenchmarks` (benchmarks of the asynchronous populations, 2018), generator `nds2016/NSGA2Tests` `GetResultsIncremental` |

Problems: DTLZ1, 2, 3, 4, 7 with 3 objectives (`dtlz3d`, data sets 1–3); DTLZ1, 2 with 4, 6, 8, 10 objectives
(`dtlzNd` / `dtlznd`, data sets 0–1); ZDT1, 2, 3, 4, 6 (`zdt`, data sets 1–3). File names are the legacy ones:
`gen10000` is the population size, `iter…` the length of the run (generational: `iter100` = 100 generations;
steady-state: `iter10000` = 10 000 iterations), `dataset<d>` an independent run; the snapshot ids inside a file are
listed in the table above.

The `FrontStorage` names come from its first use for the generational snapshots, where a "generation" is a
generation of NSGA-II and its id the generation number. In the steady-state files a "generation" is a snapshot and
its id the iteration count; in the synthetic sets, the sample index.

The snapshots are made for single-point insertion benchmarks (insert the snapshot's point into its population); the
sequences for concurrent insertion (insert the whole sequence, split round-robin over the threads). The thesis
Ch. 4 experiments measured whole NSGA-II runs, not these benchmarks.

## Changing the data

The data reproduces the thesis experiments, so files are not edited in place. When a data set is added, replaced or
removed, the same commit updates:

- [MANIFEST.tsv](MANIFEST.tsv): one tab-separated line per file — path under `src/main/resources/`, size in bytes,
  SHA-256 (`sha256sum`), git blob id (`git hash-object --no-filters`), format (`FrontStorage` or
  `DoublesAdditionProblem`), and the origin (source repository, commit and path, or the generator and its settings for
  newly generated data);
- the tables of this README (folders, counts, content);
- the tests that enumerate the data sets (`DataSetsTest` in `inds-testdata`).
